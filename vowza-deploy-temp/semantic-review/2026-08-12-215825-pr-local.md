# Restore Service Start OTP for paid pre-start bookings

The change restores Start Work for bookings the legacy payment flow has already moved to `in_progress`, treating `work_started_at` as the authoritative execution marker. The client shows the action only when its Asia/Kolkata clock says the event is due, while the database independently applies that restriction before OTP issuance and verification. OTP creation, authorization, hashing, expiry, resend limits, delivery recording, and single-use consumption remain behind authenticated Edge Functions and service-role RPCs. Customer and administrator notifications omit the OTP, and every channel accurately states that SMS is unavailable. Watch for: **confirmed, non-blocking** delivery-state ambiguity after Brevo accepts an email and **likely, non-blocking** stale-request notifications in a slow send/resend race.

**Verdict**: APPROVED

**Blockers:** none.

## High-level view

The restored state machine permits paid `confirmed`, `approved`, and legacy `in_progress` records only before work has actually started. The confirmed-bookings feed includes `in_progress`, and its water-booking normalization supplies the same time field the server uses, keeping compatible records actionable.

The server derives a timestamp from the persisted booking schedule, assigns `Asia/Kolkata`, and checks it while the booking is locked. The browser gate is consequently visual only; it cannot authorize an early start.

Calling-user identity is checked at the Edge Function and again against the assigned provider profile in the RPC. Plaintext OTPs travel only from the RPC to Brevo; delivery confirmation and participant notifications are separate commits, leaving recoverable acknowledgement races.

Add RPC and Edge Function integration tests, including water `delivery_time` and both delivery races.

<summary>Details</summary>

## Legacy pre-start state is restored without trusting the browser

`create_service_start_otp` and `verify_service_start_otp` now admit `in_progress` alongside `confirmed` and `approved`, but still require `advance_paid_at` and reject a non-null `work_started_at`. Verification writes `work_started_at` while consuming the OTP, so a concurrent verification observes an already-started service instead of creating another start.

The confirmed tab fetches `in_progress` records and Start Work requires payment plus absent start-request, completion, and start markers. Water records normalize `delivery_time` as `event_time`, matching the migration’s table-specific exception. Catering has no schedule column and remains fail-closed through `EVENT_TIME_REQUIRED`.

## India-time gate is enforced at both OTP transitions

`assert_service_start_is_due` derives the persisted date/time, applies `Asia/Kolkata`, and compares it with database `now()`. Both issuance and verification call it after `service_start_booking_context` locks the booking row. An altered browser clock cannot issue or consume a code early, and a reschedule after issuance is checked again when the OTP is entered.

The frontend accepts 24-hour and AM/PM formats only to decide whether to show the action. Missing or unparsable persisted schedules receive explicit server errors and cannot start service.

## OTP boundaries and notifications stay non-sensitive

Both Edge Functions require a bearer token; the service-role RPCs independently establish that user owns the booking’s provider profile and allow-list dynamic booking tables. The booking lock, partial active-OTP index, bcrypt hash, expiry, resend/attempt limits, delivery flag, and consume-and-start transaction preserve one active code and one service start.

Email is the only OTP-bearing channel. Vendor, customer, and administrator messages state that SMS is unavailable, and none contain the code.

## Delivery acknowledgement is not idempotent across network ambiguity

**Non-blocker — confirmed.** Brevo succeeds before `record_service_start_otp_delivery` runs. If that RPC commits but the Edge Function loses its response, the catch calls it again with `p_delivered = false`; the function permits the later call to overwrite `email_sent` and invalidate the delivered OTP. The customer has a code which verification rejects.

Make the recording function a one-way state transition that returns its existing success state on retry. The Edge Function should preserve the OTP when delivery-recording outcome is ambiguous, while still invalidating it after a confirmed email failure.

## Slow send/resend ordering can generate misleading notices

**Non-blocker — likely.** OTP creation commits before Brevo delivery. A first delivery that runs beyond the cooldown can complete after a resend has invalidated its OTP; its recorder and notification path do not require that the OTP still be active. The customer can receive two emails and notices while only the later code works.

Make delivery recording conditional on the OTP being the current non-invalidated record and use that result as the notification gate. A stale completion may be logged for observability, but must not announce an unusable OTP.

## Compatibility and failure paths are not covered by automated tests

**Non-blocker — confirmed.** No test changes accompany the migration, Edge Functions, or vendor time gate. Not tested: paid `in_progress` records with null/non-null `work_started_at`; before/at/after Asia/Kolkata event time; water versus unscheduled catering; unauthorized vendors; repeated verification; resend exhaustion; and Brevo success followed by delivery-recorder ambiguity.

Add database-level RPC tests for locking, eligibility, and OTP consumption, plus Edge Function tests with mocked Brevo and delivery recording. Assert that successful delivery cannot be downgraded and stale sends cannot publish participant notices.
