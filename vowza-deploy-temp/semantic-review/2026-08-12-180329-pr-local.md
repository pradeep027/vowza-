# Server-backed Service Start OTP integration

The vendor booking flow moves Service Start OTP generation, delivery, and verification into authenticated Edge Function calls, so vendor-side JavaScript no longer handles the plaintext code. The booking hook preserves lifecycle fields across every category and the UI adds lifecycle-gated start, entry, resend, and completion states. The OTP work is otherwise in scope, but `completeService` includes unrelated cleanup. Watch for: **likely** — Edge Function failures are collapsed into a generic network error, bypassing recovery for an already-active OTP and potentially leaving the vendor unable to enter or resend it without reloading.  
**Verdict**: NEEDS_CHANGES

## High-level view

The browser is now a thin OTP client: it submits booking identity and the entered code to authenticated functions, while the server owns authorization, code creation, hashing, delivery, and the start transition. **Confirmed:** plaintext OTP generation, storage access, and notification fan-out have left the browser; the trust boundary now relies on backend authorization and source validation, which are outside this frontend-only review.

Every normalized booking retains the request, verification, work, completion, and settlement fields. The confirmed view can therefore select the appropriate action from server lifecycle state and keep in-progress work available for completion.

The result-code UI cannot recover from errors exposed by Supabase as failures because the shared caller replaces every such error with a generic code. **Likely:** a non-2xx active-OTP response cannot reach the entry/resend state. The unrelated completion-path reformat should be split out.

### Server-owned OTP lifecycle

The service layer replaces browser-managed OTP behavior with `send-service-start-otp` for issue/resend and `verify-service-start-otp` for verification. It sends only `bookingId`, `bookingSource`, resend intent, and the vendor-entered code. **Confirmed:** removing browser OTP generation, hashing, database writes, and plaintext notifications narrows code exposure to the server-to-customer delivery path. Backend authorization and booking-source validation now have to enforce the security boundary; they were not assessed under the requested frontend-only scope.

### Function errors bypass the OTP recovery state

`callServiceStartOtp` returns a fixed `NETWORK_OR_SERVER_FAILURE` result whenever `supabase.functions.invoke` supplies `error`, without retaining `code` or `message`. The booking page only opens the entry/resend dialog after `ACTIVE_OTP_EXISTS` survives that call. **Likely:** if an endpoint uses a non-2xx response for an active, expired, unauthorized, or invalid OTP, the page renders it as an outage; an existing request remains behind the start dialog until reload. Verify that both functions use a 2xx failure envelope, or parse `FunctionsHttpError` before normalizing the result.

### Completion cleanup is outside the release boundary

`bookingExecutionService.ts` also rearranges the booking-table helper and makes cosmetic `completeService` changes to comments, an error-variable name, object formatting, and the completion message. **Confirmed:** this does not support the Service Start OTP UI/API handoff and expands review of the settlement lifecycle.

### Release validation and missing interaction coverage

`npm run build` passed and `git diff --check` reported no whitespace errors. Targeted ESLint fails on the repository’s existing `no-explicit-any` violations; the diff adds no such violation. Not tested: authenticated issue, resend, verification, active-OTP recovery, expiry, authorization failure, delivery failure, and post-verification refresh against deployed functions.
