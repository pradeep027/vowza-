# Phase 10 — Feature correctness matrix

This matrix records the correctness gates that must be exercised before release. It distinguishes tests that pass locally from checks that require a staging Supabase project, authenticated fixtures, or browser automation. It does not claim production validation.

| Feature | Happy path | Invalid / empty / error | Retry | Unauthorized / wrong owner | Current evidence | Remaining gate |
|---|---|---|---|---|---|---|
| Authentication and session restore | AuthContext session bootstrap and role resolution are covered by source behavior; the full local Vitest suite passes. | Missing role data falls back read-only to `customer`; client no longer writes `user_roles`. | Auth failures are handled without recursive role seeding. | Session expiry and cross-account role reads require staged auth fixtures. | TypeScript and 480 local tests pass. | Staging sign-up, login, logout, expiry, and wrong-account checks. |
| Provider onboarding | Profile and portfolio upload paths persist provider data; provider role assignment uses `complete-provider-onboarding` for the legacy onboarding flow. | Provider registration remains pending and no longer grants a provider role before approval. | Upload failures surface through the existing submission error path. | The Edge Function derives identity from the bearer subject and rejects a missing provider profile. | Source review and frontend build pass. | Staging storage fixtures and authenticated Edge Function tests. |
| Event planner and budget generation | Canonical event normalization and the compatibility budget adapter are covered by the planner suites. | Invalid or incomplete planner context is rejected or prompts for the missing event type. | Existing chat-flow tests cover repeated planner interactions. | Planner data is not an authorization boundary; account ownership tests remain separate. | 13 test files and 480 tests pass. | Browser-level planner journey against staging. |
| Vendor discovery and public profile | Public provider projection now excludes `vendor_details` and unnecessary profile contact fields. | Missing provider and related optional data use page error/empty states. | Page reload and React Query paths are covered indirectly by build/source checks. | Public projection still needs staging verification against the provider-public schema/view. | TypeScript and Vite build pass. | Validate the actual deployed schema/view and anonymous route renders. |
| Booking and checkout | Existing booking components and RPC paths remain unchanged by this phase. | Invalid booking data and unavailable packages are handled in the existing UI/RPC paths. | Payment/booking retry behavior needs staged provider responses. | Customer/vendor ownership and unauthorized mutations require database fixtures. | No regression detected in the 480-test suite. | Staging booking, checkout, payment failure, and owner-boundary tests. |
| KYC submission and review | Documents upload to private `verification-documents`; verification function requires bearer authentication and validates metadata. | Wrong document type, invalid metadata, excessive size, and malformed input return safe errors. | Verification retry returns a generic failure without sensitive logging. | Public profile projection omits KYC JSON; admin review uses a JWT-verified server path. | Source review, typecheck, tests, and build pass. | Staging tests for pending/approved/rejected/deleted document states and signed access. |
| Chat and private media | Chat stores object paths and signs media at read time for 300 seconds. | Malformed legacy URLs are rejected from rendering; signing failures remove the attachment URL. | Re-fetch and realtime update paths rehydrate signed URLs. | Storage policy tests require booking participation and sender-path ownership. | Local SQL chat-media regression passes; 480 tests pass. | Staging two-user access, expiry, deletion, and enumeration tests. |
| Admin and operator flows | Admin provider approval and role management use JWT-derived actors and service-side authorization. | Invalid provider IDs, actions, targets, and rejection reasons are rejected. | Admin list refresh and failed operation reload paths remain in the UI. | Admin-provider-verification and admin-user-roles reject unauthorized callers; no client actor ID is accepted. | Source review and TypeScript/build pass. | Staging admin, super-admin, self-modification, audit-log, and rollback tests. |
| Account deletion and settings | Delete-account derives the target from the authenticated session and uses canonical CORS. | Missing authorization and failed deletion return safe responses. | UI reports failure and leaves the user signed in when deletion fails. | A caller cannot supply another user ID to delete. | Source review and build pass. | Staging end-to-end deletion and data-retention verification. |

## Release interpretation

The local source and unit/integration gates are green, but this matrix is not a substitute for staging. Database policy behavior, Storage object behavior, Edge Function gateway JWT settings, Auth flows, and cross-user boundaries must be executed against a sanitized staging project before any release candidate is approved.
