# Database-first marketplace grounding for Vowza Planner

Recognized category and profile requests now route through live marketplace retrieval before any generic planning response is returned. The client validates active cards, conversation replay rehydrates saved provider IDs against current verified, published records, and exact-date searches label remaining candidates as needing confirmation rather than available. The edge function applies the intended provider predicates, but the client’s primary SQL-RPC route only receives them after the new migration is deployed. The request epoch prevents most late streaming completions from mutating a replaced thread, but it is not checked after asynchronous conversation creation. Watch for: **confirmed** unpublished yet verified profiles can still be surfaced until the hardening migration is applied; **confirmed** the edge keyword gate can replace a generic plan or budget request with a vendor search; **confirmed** a new-chat or thread switch during conversation creation can restore and populate the abandoned thread.

**Verdict**: NEEDS_CHANGES

## High-level view

Marketplace discovery now wins when a recognized profession is paired with discovery language, or when it is a short category request. The client short-circuits such turns with deterministic text and validated database cards, preventing a model response from naming or altering the returned profiles.

Current results are runtime-validated before card rendering, while saved results are re-fetched from provider and profile tables when a conversation is reopened. Both layers depend on the deployed RPC applying the same published-and-verified eligibility rule as the direct-table fallback and edge function.

Exact dates exclude only known blocked providers; every other date candidate is explicitly left as needing confirmation. The epoch guard invalidates streaming callbacks and completed responses after a conversation change, but its coverage begins too late for asynchronous initial conversation creation.

The edge function independently treats any marketplace-related word as a marketplace query. That broader classifier bypasses the client’s explicit-discovery rule and can turn a budget or planning request containing a service word into a provider-result or empty-result response.

## Marketplace routing reaches database cards before model output

`src/lib/aiOrchestrator.ts` promotes requests such as “show me decorators,” “decorator profiles,” and short category requests to `find_vendors`; it also keeps “actually, show me photographers instead” from being absorbed as a context update. `src/lib/llm.ts` retrieves before returning structured VEDA output, then emits deterministic text and `vendor_results` from the same validated `dbVendors` collection. This gives category/profile discovery database-first precedence over generic plans and prevents either model path from composing vendor records.

The server is more permissive than that client contract. `supabase/functions/ai-chat/index.ts` sends every last user message matching `MARKETPLACE_TERMS` into `retrieveMarketplaceVendors`, even if it lacks discovery language. A message such as “plan my wedding budget including catering” is classified as a budget request by the client and does not request client retrieval, but its edge call matches `catering` and returns caterer results instead of a budget. A request containing only `availability` or `booking` has no profession filter, so it gets the no-results message asking for a category and city. **confirmed**: the endpoint can hide the requested planning answer.

## Published-provider enforcement depends on a migration that is not live

Active cards pass `dedupeVerifiedDBVendors`, and persisted cards are re-fetched through `rehydrateVerifiedDBVendors` in `src/lib/conversationRepository.ts`. The direct provider-table queries require approved/verified status, `is_verified`, and `is_published`, so saved cards are database-validated again when history is restored.

The normal client query does not use that direct fallback when the existing `search_vendors_sql` RPC succeeds. Its prior definition in `20260802000000_rag_vector_search.sql` filters only `verification_status`; it can return a row whose `is_verified` is false or whose `is_published` is false. The added migration closes both gaps, but its header says it is intentionally additive and not applied by this local fix. The runtime validator removes false `is_verified` values, but it has no publication field and retains a verified, unpublished profile. **confirmed**: until this migration is deployed, visible/published filtering is not consistently enforced and a hidden profile can be displayed through the primary retrieval route.

`retrieveMarketplaceVendors` in the edge function returns `[]` when its provider query errors and ignores errors from the profile and date-availability lookups. `buildGroundedMarketplaceResponse` then uses the ordinary “couldn’t find any verified vendors” message. **confirmed**: an outage, schema error, or denied query is presented as an empty marketplace, an unsupported claim that can cause users to abandon a valid search. The client retriever distinguishes `technical_error` and uses `VENDOR_SEARCH_UNAVAILABLE_MESSAGE`; the edge boundary should preserve that distinction.

## Date searches remain conservative rather than inventing availability

`src/lib/aiOrchestrator.ts` records an ISO or named exact date, while a month-only statement remains a non-date planning value. `src/lib/ragRetriever.ts` checks matching `provider_availability` blocks only for exact dates, excludes known unavailable candidates, and marks every remaining candidate `needs_confirmation`; database/RLS errors follow the same label. `supabase/functions/ai-chat/index.ts` follows the same policy. An unblocked calendar row is never presented as proof of availability, including where a booking conflict has not been queried.

## Most stale completions are rejected, but the first persistence await is unguarded

`src/components/ai/useAIChat.ts` increments `requestEpochRef` on a send, clear, deletion, and conversation selection. Streaming chunks, the resolved AI response, and errors compare their captured epoch and conversation ID before changing message state, cards, context, or persisted assistant history.

The captured epoch is not checked immediately after `await createConversation(...)`, and `isStreaming` is set only after that await. If a user starts their first message and immediately clears the chat or opens another conversation while creation is pending, the stale send assigns the returned ID to `convIdRef`, session storage, and state, then writes the user message and starts streaming. Its later completion passes the conversation-ID check because the stale request itself restored that ID. **confirmed**: the abandoned conversation can become active again and receive its response.

## Coverage verifies routing and ranking, not the trust boundaries

`src/lib/plannerRecommendation.test.ts` verifies the intended category routes, ranking reasons, and “needs confirmation” status. The configured focused suite also passes the vendor-trust tests. Not tested: migration application against the RPC, edge handling for generic planning terms and query failures, or a delayed `createConversation` followed by clear/switch; those are the paths behind the outstanding defects.
